# 故障排查与未完成事项

按症状定位到责任层，再核对实际版本。优先保存失败回执与原始录制，避免为了得到绿色状态修改事实。

## 常见症状

| 症状 | 先检查 | 判断与处理 |
|---|---|---|
| GUI 选择 HighEvidence 但缺资源 | 目标启动参数、loaded_ini、effective config、Catalog/Frame 引用 | 连接已有进程不应用新 INI；当前默认与独立 HighEvidence 不同 |
| 连接成功但没有场景负载 | 登录/业务就绪、Player 日志、稳定帧、图形状态 | 进程与 Init 场景不证明真实进服 |
| stream 无法被 analyze 打开 | store 是否发布、schema17、源身份、EXE | analyze 不自动走 Query 的无 store 重放 fallback |
| 安装后报哈希不符 | stream-local、实际 EXE、安装前后清单 | 可能保留了新配置却复制回旧包 EXE；先恢复一致工具组合 |
| analysis_process_memory_budget | 实际 EXE SHA、manifest.memory、private 与系统余量 | 区分 4/16/32 GiB 身份；VRAM 阈值不控制进程内存 |
| Query 归并文件流耗尽 | 分支是否含 f62bd2d69、实际 EXE 与对应日志 | 修复在 dev 后续历史，mainline 不应被默认为已有 |
| 普通 .tracy 无法打开 | 标准/扩展格式、reader 版本、具体错误、规模 | 转换成功不等于全部 GUI 路径可承受该规模 |
| Query 返回 0 或空列表 | capability、present、partial、分页、单位 | 先排除未填写字段/单位差异；不能直接认定原始数据丢失 |
| 没有动态调用栈 | 事件来源、SourceStack/Native 栈、实际深度与预算 | SourceLocation 存在不等于逐事件 unwind；现有作用域仍可定位 |
| GPU 容量不高却有长等待 | residency 状态、预算、真实策略、driver/CPU 侧 | 低显存用量不能直接排除驱逐或其他同步 |
| 网页无限定位中/无画面 | 当前 navigation、renderer、实时帧到达、端口、标签共享状态 | 原生 ready 或 HTTP 200 不足；检查 framebuffer/通道与浏览器实际绘制 |
| 网页模糊或命中位置错误 | PNG 原图、CSS 尺寸、DPR、显示模式 | 1:1 与适应宽度分开，坐标必须映射回原图 |
| 报告帧号与 GUI 不同 | FrameSet、Query index、GUI 显示号 | 不统一加一，不把 EventStore ID 当 Query ref |
| 两次报告数值/条数不同 | capture、工具/算法、阈值、分母、full/clipped、归并规则 | 先统一统计口径；再检查遗漏、取样与解释差异 |
| 新 Player 无法启动或卡住 | DLL/PDB/metadata、包映射、资源契约、日志/挂起栈 | 同公共 Unity 版本不证明兼容，不能只换单文件试错 |

## 旧验收遗留如何继承

R20 的冷建恢复、跨进程磁盘账本、GPU Frame Evidence 和 Ghost 全量 MCP 导出未在当时关闭。新 gpu.frame.resources 或 EventStore 并不按名字自动替代这些合同；需要将具体查询字段、输入规模和验收目标逐项映射后再关闭旧项。

N27/N28 的真实来源链、性能和零语义影响验证也应按实际使用的路径重新定位。默认关闭某个高开销功能可以改变使用策略，但不能把该功能原有未通过项改成通过。

## 排查记录建议

保存最小输入或定位窗口、实际 EXE/源码身份、复现命令、明确错误、原始与预期字段、负向/正向结果、资源采样与影响范围。修复后使用新运行目录，不覆盖失败证据。对于数据质量问题，先确定发生在 producer、持久化、读取、统计还是报告层，再选择修复位置。
