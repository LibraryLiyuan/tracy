# 分析方法 证据强度与报告质量

性能报告需要解释具体成本和可执行的下一步。函数名、源码片段、截图和校验数量都不能单独证明诊断深入。

## 判断层级

| 层级 | 可以陈述的内容 | 还缺什么 |
|---|---|---|
| scope_located | 成本出现在某个帧、线程、作用域或资源范围 | 内部机制、执行与等待、业务上游 |
| mechanism_supported | 源码和证据支持某个机制解释 | 运行条件、对象身份或可比反证 |
| runtime_cause_verified | 本次现场存在可复核因果链 | 优化后收益与功能影响 |
| benefit_measured | 同条件复测证明实际收益 | 仍应限定场景和版本 |

这四层来自新原因调查合同。不要把“全严重帧有窗口”当作全部根因完成，也不要把多个建议收益相加承诺稳定 60 FPS。[cause-investigation.md:1](../skills/diagnose-jn-unity-tracyV2/references/cause-investigation.md#L1)

## 数值口径

| 数值 | 必须保留的范围 |
|---|---|
| 帧耗时与分位 | FrameSet、完整帧分母、算法、是否排除尾帧 |
| CPU inclusive/self | 完整事件或帧内交集、合法层级、线程；self 不自动等于 on-CPU |
| 调用次数 | 原生计数、统计窗口、是否唯一实例；不能把 ns 当次数 |
| GPU 时间 | queue、timestamp/Segment、并发与跨帧范围；不等于 CPU 提交时间 |
| 显存 | DXGI/物理/逻辑/引用集合、采样时刻、Local/NonLocal/UMA |
| 进程内存 | private commit、resident working set、系统 commit；不能相加 |
| 执行时长 | 工具计时、整个阶段跨度、等待/重试/构建是否包含 |

未知、未记录、未查询和零值分别表达。父子、不同线程、不同 Queue 和 CPU/GPU 异步成本不能直接相加。5 GB 与 5 GiB 明确区分。

## 每个主要问题的六段结构

1. **结论与影响**：现象、范围、成本和确认程度。
2. **样本与证据**：实际帧/线程/事件、数值表、正常或反例、原生图片及入口。
3. **机制与源码**：Marker 覆盖范围、具体调用/等待链、条件和已有控制。
4. **假设与反证**：支持、排除与仍不能区分的原因。
5. **处理或补证方案**：具体修改对象或数据，以及它能区分什么问题。
6. **复测标准**：控制条件、指标、支持/否定标准和功能检查。

这是交接建议采用的共同阅读结构；当前 Skill/生成器各分支的实际字段与实现状态见相应章节，不能因文档建议就宣称生成器已经强制实现全部要求。

## 不同问题往哪里追

| 入口 | 下一层应核查 |
|---|---|
| Main/Render 等 Job | 同窗口 Worker、ActiveHelp、依赖/完成端和真正昂贵实例 |
| Shader/PSO | 编译还是 driver 创建、预热资产生成与加载、质量路径、cache key、唯一变体身份 |
| 通用 CreateResource/Upload/Release | 上游 caller、具体资源、大小、lifetime、已有复用和 dirty gate |
| 锁或 Async API | 真实持锁侧、共享上下文、锁内工作和释放；时间重叠只建立假设 |
| UI/Awake/加载 | 具体组件、prefab 默认依赖、同步加载、池初始化和分帧机制 |
| Residency 停顿 | 状态曲线、预算、aging/pressure/driver 路径；低用量不排除驱逐 |
| 多管理器预算 | 单实例还是全局、真实实例身份、单次操作能否跨越预算 |
| 稳态慢 | 低单次高频成本、参数设置、整 Buffer 上传、小分配、提交和回收 |

## 历史反例应成为回归用例

- 曾选择 0.009 ms 的 Job 实例，而同帧已有 130.606 ms 长任务和 129.584 ms 等待证据：类型正确不足以证明实例选对。
- 曾把同一 689 ms 长帧中的 8.38 ms VSync 区间当正常对照：数值低于预算不证明样本可比。
- QS16B 的 818 条和 QS17 的 73 条观察各使用同一句下一步：应对逐原因提出可区分的假设和动作。
- 已发现的长 Job—主线程等待链只留在后来隐藏的发现过程：正式正文必须保留关键结论。
- 单项复测把 ns 成本标为调用次数仍被旧校验接受：需要语义校验，不能只比数值。[Tracy分析与报告质量深度评审.md:1](C:/Users/Admin/Documents/JN-Unity-T3/Skill-Quality-Review-20261008/Tracy分析与报告质量深度评审.md:1)

## 补充插桩如何设计

先沿源码 → 配置 → producer → 持久化 → Query → 报告核查信息是否已经存在。若 Shader 创建区间混合锁、复制、设备调用、发布和重复销毁，需要的是分阶段计时、输入规模、分支结果、请求身份与完成关系，而不是泛泛“增加 Marker”。[插桩分析与报告格式约束建议.md:1](C:/Users/Admin/Documents/JN-Unity-T3/Skill-Quality-Review-20261008/插桩分析与报告格式约束建议.md:1)

优先使用现有字段并说明仍缺的最小证据。新增插桩同时验未连接开销、启用开销、重连、容量、Begin/End 配对和业务语义，不能只看新事件有没有出现。

## 交付时的人工复核

逐项核对报告有无遗漏已经取得的关键字段，是否保留有效旧发现，优先级和计时口径是否一致，图片是否绑定同一实例，建议是否具体可检验。schema/lint/链接检查只证明结构层次，不能代替因果复核。
